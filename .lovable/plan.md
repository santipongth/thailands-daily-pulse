# ปรับสัญญาณให้ทันกับข้อมูลที่มาจริงทุกหมวด

## เป้าหมาย
เมื่อข้อมูลหรือประกาศผิดปกติมาช้ากว่าวันที่อ้างอิง ให้ตรวจตามจังหวะเผยแพร่จริงและยังค้นพบได้ในวันที่ระบบได้รับ โดยไม่ปลอมวันที่ข้อมูล ไม่สร้างสัญญาณจากค่าที่ไม่เกินเกณฑ์ และไม่เพิ่มการ์ด “ใกล้เกณฑ์” กลับมา

## สิ่งที่จะทำ
1. ตรวจทุกหมวดที่มีเกณฑ์สัญญาณ (อากาศ ฝุ่น น้ำ น้ำมัน ค่าเงิน ทอง อาหาร เกษตร จราจร ค่าไฟ รถไฟฟ้า และประกาศตามรอบ) เทียบวันข้อมูล วันเผยแพร่/วันรับจริง ความถี่และช่วงขาดข้อมูล แยกหมวดที่ใช้เพื่อเปรียบเทียบอย่างเดียวออกจากหมวดที่แจ้งสัญญาณ
2. ปรับกรอบเวลารับข้อมูลต่อแหล่งตามประวัติการมาจริงและรอบเผยแพร่ โดยใช้ค่าเริ่มต้นที่ปลอดภัยเมื่อประวัติยังน้อย; เทียบกับค่าก่อนหน้าเฉพาะเมื่อห่างกันสมเหตุสมผล และไม่ใช้ค่าค้างเป็นเหตุการณ์ใหม่ทุกวัน เกณฑ์ขนาดการเปลี่ยนแปลงเดิมยังคงอยู่ เว้นแต่การตรวจสอบพิสูจน์ว่าต้องปรับเพื่อแก้การตัดทิ้ง
3. เมื่อข้อมูลเกินเกณฑ์แต่เข้าช้า ให้บันทึกวันที่ข้อมูลเดิมควบคู่เวลาที่ได้รับ และแสดงใน “สัญญาณวันนี้” ของวันรับจริงแบบระบุว่าเป็นข้อมูลมาช้า พร้อมประวัติ/ฉบับแก้ไขโดยไม่ซ้ำกับสัญญาณเดิม; สรุปเช้าที่ปิดรับข้อมูลแล้วไม่ถูกแก้ย้อนหลัง และสัญญาณหลังปิดรับต้องไปอยู่ในอัปเดตหลังเผยแพร่ด้วย
4. รถไฟฟ้า: เก็บข้อความผิดปกติเต็มทุกชิ้นพร้อมเวลาโพสต์ เวลาได้รับ และเหตุผลที่นับ/ไม่นับ; ประกาศเหตุขัดข้องหรือล่าช้าที่เข้าช้าต้องแสดงให้เห็นในวันที่รับจริง ไม่หายไปเพราะข้ามเที่ยงคืนหรือช่องว่างระหว่างรอบตรวจ ส่วนข่าวปิดทางเข้า/เปลี่ยนเวลาเดินรถยังเป็นบริบท ไม่ยกเป็นสัญญาณโดยไม่มีเหตุบริการผิดปกติ
5. ทำรายการตรวจสอบรายตัวชี้วัดและทดสอบวันเดียวกัน/ข้ามวัน/ข้ามวันหยุด/มาเกินรอบ/ข้อมูลขาด/ประกาศซ้ำ/หลัง 05:45 และดูหน้าวันนี้ทั้งมือถือกับจอใหญ่ ตรวจว่าแสดงเฉพาะสัญญาณที่เกินเกณฑ์พร้อมที่มาและวันข้อมูลจริง

## รายละเอียดทางเทคนิค
- จากโค้ดปัจจุบัน `detect_core` อนุญาต `lag_days` เฉพาะตัวชี้วัดอาหารแบบรายสัปดาห์; ตัวอื่นค้นค่าเฉพาะ `observed_on = วันปัจจุบัน` แม้ข้อมูลเผยแพร่ทีหลัง และการตรวจซ้ำหลังดึงข้อมูลรันแค่วันนี้กับเมื่อวาน. จะขยายกติกาความสดและการประมวลผลย้อนหลังแบบจำกัดช่วง พร้อมบันทึกเหตุผลใน `checks` และคงขอบเขตสิทธิ์การเขียนไว้ฝั่งผู้ดูแล/งานระบบ
- `classifyRail` เก็บประกาศช้าเป็น `late` แต่ค่าเหตุการณ์รายวันนับเฉพาะ `counted` ของวันนี้; จะแยก “เหตุเกิดเมื่อไร” กับ “พบเมื่อไร” อย่างตรวจสอบย้อนกลับได้ และคงการไม่นับบริบทตามกติกาเดิม
- หน้าปัจจุบันแยก `release` ไปส่วน “ประกาศใหม่วันนี้” และกรอง `moves` ตามความสำคัญ/แหล่งที่ผู้อ่านเลือก; จะทำให้สัญญาณมาช้าที่เกินเกณฑ์ปรากฏในส่วนที่เหมาะสมโดยไม่ฝืนการตั้งค่าของผู้อ่าน
- ใช้ migration สำหรับการเปลี่ยนกฎฐานข้อมูล พร้อมทดสอบย้อนหลังจากข้อมูลจริงและกรณีจำลอง; ไม่สร้างข้อมูลตัวอย่างขึ้นแสดงเป็นข้อมูลจริง
