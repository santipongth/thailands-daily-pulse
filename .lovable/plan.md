# ปรับทั้งเว็บไซต์ให้เป็นระบบภาพเดียวกันและรองรับทุกหน้าจอ

## เป้าหมาย
ทำให้ทุกหน้าใช้ภาษาออกแบบเดียวกับหน้า “วันนี้” โดยนำโครงสร้างแบบ **Unified tactile dashboard** ที่เลือกมาใช้กับลำดับข้อมูล พื้นผิว และความชัดเจน แต่ยังคงโทนกระดาษ หมึกดำ และแดงบรรณาธิการของ Thailand Daily Signals

## 1. สองส่วนบนหน้า “วันนี้”
- ปรับ “ตัวอย่างค่าใช้จ่ายครัวเรือนต่อวัน” และ “ผลสลากงวดล่าสุด” ให้ใช้โครง section เดียวกัน: หัวข้อ แถบเน้น สรุปตัวเลขหลัก กลุ่มรายละเอียด และข้อความกำกับ
- ใช้พื้นผิวและความลึกแบบ tactile อย่างพอดี โดยไม่ทำเป็นการ์ดซ้อนหลายชั้นและไม่เปลี่ยนค่าข้อมูลจริง
- ทำตารางค่าใช้จ่ายให้อ่านง่ายบนมือถือ และจัดเลขสลากให้เด่นโดยไม่ล้นจอ
- ลบข้อความ “(คำนวณโดยระบบ ไม่ใช่ AI)” ตามคำขอ โดยคงคำอธิบายสูตรและแหล่งข้อมูลที่จำเป็น

## 2. ระบบภาพกลางสำหรับทุกหน้า
- สร้างชุดรูปแบบร่วมสำหรับกรอบหน้า หัวหน้า คำโปรย หัวข้อ section เส้นคั่น แผงข้อมูล ตาราง กราฟ ป้ายสถานะ และ empty/error states
- ใช้ฟอนต์หลักเดียวกันทั้งเว็บ: IBM Plex Sans Thai สำหรับเนื้อหา และฟอนต์บรรณาธิการเดิมเฉพาะหัวเรื่องสำคัญ
- คงสี semantic เดิมและเพิ่มเฉพาะ token สำหรับพื้นผิว เงา และระดับความลึก จึงยังรองรับธีมและ contrast อย่างถูกต้อง
- ปรับ masthead, footer, เมนูมือถือ และข้อความแจ้งเตือนให้เข้ากับระบบเดียวกัน

## 3. ปรับครบทุกหน้าที่ผู้ใช้เข้าถึง
- ใช้ความกว้างหลัก `max-w-6xl` และระยะขอบมาตรฐานกับหน้า Today, Brief, ข้อมูลสำคัญ, ข้อมูลทั้งหมด, รายวัน, หน่วยงาน, เหตุการณ์, สูตรผลกระทบ, ปฏิทิน, ข้อมูลดิบ, ไฟล์ดิบ, วิธีคำนวณ, แหล่งข้อมูล, ติดตามข้อมูล, ตั้งค่า, Sitemap และ Developer Document
- หน้าที่ต้องอ่านยาว เช่น Brief และรายละเอียดเหตุการณ์ จะคงความกว้างบรรทัดที่อ่านสบายภายในกรอบเต็มหน้า ไม่ยืดข้อความจนอ่านยาก
- จัดตารางและกราฟให้ใช้หัวข้อ คำอธิบาย สี เส้นกริด และสถานะ “ไม่มีข้อมูล/ตรวจไม่ได้” แบบเดียวกัน
- ปรับหน้า 404 และหน้าข้อผิดพลาดเป็นภาษาไทยและใช้ภาพลักษณ์เดียวกับเว็บ
- ไม่เปลี่ยนตรรกะ Signal, ranking, cutoff, household impact, cron, API หรือ MCP

## 4. Responsive web
- ตรวจตั้งแต่จอมือถือ 320/390px, tablet 768px ถึง desktop 1280px ขึ้นไป
- แถวที่มีข้อความกับปุ่มใช้ responsive grid; ตารางเลื่อนได้เฉพาะภายในพื้นที่ตาราง; กราฟมีความสูงและแกนที่เหมาะกับแต่ละขนาด
- ป้องกันข้อความ ตัวเลขยาว แผนที่ กราฟ และ navigation ล้นหรือทับกัน
- รักษาเมนูมือถือและ footer ให้ใช้งานได้ด้วยแป้นพิมพ์และมีขนาดกดเหมาะสม

## 5. การเก็บข้อมูล
- คงสถาปัตยกรรมตามตัวเลือกที่ยืนยัน: ข้อมูลเชิงโครงสร้างทั้งหมด เช่น observations, signals, briefs, ประวัติ, สถานะแหล่ง และดัชนีหลักฐาน อยู่ใน PostgreSQL
- ไฟล์ดิบจริงและภาพ Brief ยังคงเก็บในพื้นที่ไฟล์ส่วนตัว; PostgreSQL เก็บ path, hash, metadata และความสัมพันธ์กับข้อมูล เพื่อค้นหา ตรวจสอบ และ deduplicate ได้
- คงการตั้งค่าส่วนบุคคลไว้ในอุปกรณ์ เพราะระบบไม่มีบัญชีผู้ใช้ และไม่ส่งข้อมูลส่วนบุคคลขึ้นฐานข้อมูลโดยไม่จำเป็น
- ตรวจทุกเส้นทางบันทึกข้อมูลว่ามี metadata ใน PostgreSQL และไม่มีไฟล์ดิบหรือ path ส่วนตัวหลุดผ่าน Public API/MCP

## 6. การตรวจรับ
- ตรวจ metadata ของทุก content route ให้มี title, description, Open Graph และ Twitter card เฉพาะหน้า
- ตรวจ TypeScript และผลสร้างเว็บไซต์
- เปิดทดสอบทุกหน้าหลักทั้งมือถือ tablet และ desktop พร้อมตรวจ horizontal overflow, console error และหน้าที่มีตาราง/กราฟ
- ตรวจ REST API, OpenAPI และ MCP 17 tools ว่ายังคงอ่านอย่างเดียว และไม่เปิดไฟล์ส่วนตัว งานคิว หรืองานเขียนข้อมูล
- ไม่เผยแพร่เว็บไซต์จนกว่าจะตรวจครบ และจะรายงานหากยังมีคำเตือน dependency ของ MCP ที่แก้จากฝั่งแอปไม่ได้
